# Independent verification — FAIL

Verified 2026-08-29 against candidate commit `83dd4449cd3513ee484be0885bc593d272918185` and the live URL <https://end-client-reference.sociobot.in>.

## Verdict

**FAIL — do not release this candidate.** The normal free cover-sheet workflow works, but mandatory acceptance requirements are missing and the public paid checkout is non-functional.

## Mandatory claims and demo gate

- `.factory/claims.json` is absent in the clean candidate. Therefore there were no declared claim commands to run from a demo entry point. This is release-blocking under the claims contract.
- `.factory/demo.md` is also absent. `/?demo=1` opens the normal empty workspace; it has no sample data, no `Demo — sample data, nothing is saved` banner, no reset/start-for-real controls, and does not use a separate demo storage namespace.
- Cold first read of the live page: it appears to make a companion relationship cover for an invoice so an end customer is clear. It does not say that this is for subcontractors, fractional specialists, or white-label agencies, and it gives no first-screen action. In particular there is no one-click **Try it with sample data** action anywhere. This independently fails the plain-words/demo gate.
- The live landing and README make testable claims including “Runs on your device”, “Keeps the original invoice intact”, “Works offline after first visit”, “No analytics”, and “No cloud document storage”; none can be represented in a missing claims manifest.

## Environment and candidate identity

- Started from a clean checkout at the exact candidate commit; installed with `npm ci` (60 packages, 0 audit vulnerabilities).
- `npm test` passed: 2 Vitest tests and 5 Playwright tests.
- `npm run build` passed (TypeScript check plus Vite production build) and produced `dist/`. There is no separate lint script.
- Hashes of local `dist/index.html`, both entry assets, the lazy PDF asset, `sw.js`, and `manifest.webmanifest` exactly matched the files fetched from the live URL. The live deployment therefore matches this candidate; the reported deployment-only failure was not reproduced.

## Privacy, PWA, accessibility, and performance evidence

- During the complete ordinary generation and CSV-export flow, the Playwright request log contained only same-origin requests: document, CSS/JS, icon, manifest, artwork, and the lazy PDF chunk. There were no outgoing third-party or billing requests. This supports the normal-flow privacy behavior, but does not cure the absent claim test.
- Live response headers provide HSTS, `Referrer-Policy: strict-origin-when-cross-origin`, and `X-Content-Type-Options: nosniff`. They do not provide a Content-Security-Policy. Hashed assets are served as `cache-control: public, must-revalidate, max-age=30`, not long-lived immutable assets.
- The live PWA registered `performed-for-4e177b6f9769`; after it controlled the page, offline reload showed the workspace and the Offline notice. A locally isolated copy of the exact built output was then updated to a new worker build ID: the app showed “A fresh map is ready. Reload when convenient.” and installed the new cache. PWA update behavior passed.
- Playwright axe found no serious or critical issues on the live workspace. Keyboard Tab reached the skip link, navigation, file input, relationship inputs, generate button, license link, and export controls; Enter generated the package. At 390 × 844 there was no horizontal overflow (`scrollWidth == clientWidth == 390`). No page errors or console errors occurred in the exercised flows.

## Billing and rate-limit evidence

- The live `Buy the one-time unlock` href is `https://pilot-api.sociobot.in/api/v1/products/end-client-reference/checkout`. A fresh GET to that exact URL returned **404**. The production site must use `https://api.sociobot.in/api/v1/...`; staging `pilot-api` is only appropriate before release.
- A single client made invalid-token verification requests to the configured pilot endpoint. Requests 1–30 returned 200 invalid verdicts; request 31 returned **429** with `Retry-After: 4`. Observed allowance: 30 requests per rate window (the window duration is not advertised). Thus the configured verification endpoint did enforce the required throttle, although it is the wrong host for the public deployment.
- The product has no sign-in flow, so Entra tenant verification is not applicable.

## Defects

### Critical

1. **Missing claims manifest and test coverage.** `.factory/claims.json` does not exist, so every public claim is unregistered and no required claim test can run from a clean demo sandbox.
2. **No one-click isolated sample demo.** There is no `Try it with sample data`, direct demo data, demo banner, reset/start-real controls, or `?demo=1` behavior. The first screen therefore fails the explicit acceptance gate.
3. **Broken public paid checkout.** The deployed unlock link uses the staging pilot API and returns 404. This makes the advertised $19 one-time purchase unavailable and violates the paid-unlock contract.

### High

1. **Long allowed client/reference values are silently truncated on the generated cover.** Inputs permit 180/220 characters, but `src/pdf.ts` draws only `lines.slice(0, 3)` for the billing client, end client, and PO/reference. This violates the brief's requirement to preserve names and POs exactly as entered.
2. **Required relationship fields accept whitespace-only values.** A real PDF plus three fields containing spaces generated and logged a blank relationship, rather than explaining what must be entered. This permits unusable cover sheets and reports.

### Medium

1. **Security and cache headers are incomplete.** Live documents and assets lack CSP, and hashed assets are only cached for 30 seconds rather than `immutable` long-term caching.
2. **Route metadata and not-found behavior do not meet the site contract.** `/privacy` and `/terms` retain the workspace title rather than route-specific titles; the site has no canonical/OG metadata; `/does-not-exist` returns the workspace with HTTP 200 instead of a real, styled 404.

## What passed

The core free local workflow, exact relationship log/CSV export for representative Unicode data, validation recovery, free-limit messaging, offline reload, service-worker update prompt, PWA manifest/icons, normal-flow request privacy, keyboard operation, mobile layout, serious/critical axe scan, no observed console/page errors, unit/e2e suite, type check, build, and audit all passed.

## Required before re-verification

1. Add an isolated one-click sample demo and its documentation, then add `.factory/claims.json` with one runnable demo-entry test for every claim.
2. Build the production deployment with the production Sociobot billing base and verify its checkout link returns the hosted checkout.
3. Preserve all permitted input text in the cover (or constrain values with a clear pre-generation validation) and reject whitespace-only required fields.
4. Add CSP and immutable cache headers, real 404 handling, and required per-route metadata.
